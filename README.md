# howami

> "오늘 나, 어때?" — AI 에이전트와 함께하는 로컬 퍼스트 데일리 자기진단

매일 5분, AI 에이전트가 하루를 묻는다. 점수가 떨어진 항목만 골라 원인을 함께 파고,
내일 바꿀 행동 하나를 정한다. 기록은 **내 PC의 마크다운 파일**로 남고,
조회용 SQLite가 그 옆에 따라붙는다. 서버도, 계정도, 텔레메트리도 없다.

```
> /howami

오늘 하루 어땠어요? 먼저 가볍게 훑어볼게요. 에너지는 1~5 중 몇 점이에요?
< 2점

어제는 4점이었는데 많이 떨어졌네요. 언제부터 그랬어요?
< 오후 회의 끝나고부터...

그 회의에서 무슨 일이 있었는지 조금 더 말해줄래요?
...

정리하면 원인은 "준비 없이 들어간 회의에서의 자책"으로 보여요.
내일 바꿀 수 있는 딱 하나를 정한다면?
< 회의 10분 전에 아젠다 훑기

오늘은 평소 평균과 비교해 에너지가 떨어진 걸 먼저 잡았고, 언제부터였는지 좁혀서
오후 회의를 시작 지점으로 봤어요. 거기서 왜를 세 번 따라 내려가 "아침에 캘린더를
안 본다"까지 갔고, 바꿀 수 있는 쪽이라 처방으로 뒀어요.
저장했어요. (~/howami/data/2026-08-27.md)
```

결론만 던지지 않고 **어떤 기법으로 그 결론에 닿았는지**까지 남긴다.
나중에 기록을 다시 볼 때 "왜 이런 얘기가 나왔더라"를 되짚을 수 있어야 하기 때문이다.

## 왜 만들었나

감정과 멘탈은 가장 민감한 개인정보인데, 기존 기록 앱은 대부분 그걸 서버에 올린다.
고정된 설문은 기계적이라 사흘이면 안 하게 되고, 기록만 쌓일 뿐 "왜?"를 파고들지 않는다.
원인이 빠진 기록은 일기일 뿐이다.

AI 에이전트가 생기면서 세 문제가 한꺼번에 풀렸다. 대화형이라 설문보다 이어가기 쉽고,
답에 따라 후속 질문을 동적으로 던질 수 있고, 로컬 파일만으로 돌아가니 서버가 필요 없다.

## 설치

Python 3.8 이상만 있으면 된다. 외부 패키지는 쓰지 않는다.

```bash
git clone https://github.com/<user>/howami.git
cd howami
./install.sh          # 레포를 ~/.claude/skills/howami 로 심볼릭 링크한다
```

Claude Code를 재시작한 뒤 `/howami` 또는 "오늘 나 어때"라고 말하면 시작된다.

데이터 위치를 옮기고 싶으면 `HOWAMI_HOME` 환경변수를 잡는다.

```bash
export HOWAMI_HOME=~/Dropbox/howami   # 동기화가 필요하면 이런 식으로 각자 알아서
```

## 어떻게 동작하나

진단은 3단계다.

| 단계 | 하는 일 | 시간 |
|---|---|---|
| **스캔** | 5개 항목(에너지·기분·수면·계획 실행·관계)을 점수만 받는다 | 1분 |
| **탐지** | 낮거나 급락한 항목 하나만 골라 트리거 → 생각 → 감정 → 행동 → 왜 체인으로 판다 | 3분 |
| **처방** | 내일 바꿀 딱 하나를 사용자가 정한다. 다음 날 실행 여부를 확인해 루프를 닫는다 | 1분 |

전부 괜찮은 날은 탐지를 건너뛰고 1분 만에 끝난다. 좋은 날까지 파고들 이유가 없다.

### 진단 기법은 기록에 남는다

각 단계에서 실제로 밟은 기법을 [`questions/methods.yaml`](questions/methods.yaml)의
id로 남긴다. 기준선 비교, 트리거 특정, 사고기록, 5 Whys, 통제 이분법, 행동 활성화,
최소 단위로 쪼개기, 실행 의도 등 10가지가 기본으로 들어 있고, 각 항목에는
출처와 "사용자에게 어떻게 설명할지"(`say_it_as`)가 함께 적혀 있다.

덕분에 나중에 이런 것들을 알 수 있다.

- 이 결론은 어떤 경로로 나왔나 (그날 기록의 `## 참고한 기법`)
- 나는 주로 어떤 방식으로 진단받고 있나 (`stats`의 기법 빈도)
- 5 Whys까지 간 날과 스캔만 하고 끝난 날은 무엇이 달랐나 (SQL 한 줄)

임상 척도나 치료 기법의 이름을 빌려 온 항목이 있지만, 전부 일상 언어로 재작성해
참고할 뿐이다. 치료를 대신하지 않는다.

## 저장 구조

```
~/howami/
├── data/
│   └── 2026-08-27.md   # 하루 한 파일. 원본이자 사람이 읽는 문서
├── howami.db           # SQLite. md에서 파생되는 조회용 인덱스
└── insights/           # 주간·월간 패턴 리포트 (요청할 때 생성)
```

**md가 원본이고 DB는 캐시다.** DB를 통째로 지워도 `sync --rebuild` 한 번이면
md에서 완전히 복원된다. 반대는 성립하지 않는다.

md를 에디터로 고치거나 다른 기기에서 git으로 받아와도, 다음 호출 때 mtime을 보고
자동으로 다시 읽어들인다. 그래서 원본을 그냥 열어서 읽어도 되고, grep 해도 되고,
git으로 버전 관리해도 된다.

DB가 하는 일은 조회다. "수요일마다 에너지가 낮은가", "5 Whys까지 간 날은 며칠인가"
같은 질문에 SQL 한 줄로 답할 수 있고, 기록이 몇 년치 쌓여도 느려지지 않는다.
쓰기는 막혀 있다. 원본을 우회해 DB에만 남는 데이터가 생기면 안 되기 때문이다.

자세한 형식과 테이블 구조는 [`schema/daily.md`](schema/daily.md)에 있다.

## 저장소 구조

```
howami/
├── SKILL.md            # 진단 로직 (에이전트가 읽는 프롬프트)
├── questions/          # 질문 세트와 기법 카탈로그 = 데이터
│   ├── core.ko.yaml
│   ├── core.en.yaml
│   └── methods.yaml    # 진단 기법 10종 (id·출처·설명 문구)
├── scripts/howami.py   # 저장소 계층. 읽기·쓰기만 하고 대화는 하지 않는다
└── schema/daily.md
```

**질문(데이터)과 진단 로직(프롬프트)을 분리한 것이 이 프로젝트의 뼈대다.**
자기 언어나 상황에 맞는 질문 팩을 추가하고 싶으면 `questions/`에 파일 하나만 더하면 된다.
로직은 건드릴 필요가 없다.

## CLI로 직접 쓰기

에이전트 없이도 데이터를 다룰 수 있다.

```bash
python3 scripts/howami.py context --days 14   # 최근 기록 요약 (에이전트가 대화 전에 부른다)
python3 scripts/howami.py stats --days 30     # 요일별 평균, 추세, 처방 실행률, 기법 빈도
python3 scripts/howami.py sync --rebuild      # md에서 DB 전부 재생성
python3 scripts/howami.py where               # 경로와 DB 상태 확인

python3 scripts/howami.py query --sql "
  SELECT e.weekday, ROUND(AVG(s.value),2) AS mean
  FROM scores s JOIN entries e ON e.date = s.date
  WHERE s.key = 'energy' GROUP BY e.weekday ORDER BY mean"
```

`query`는 `SELECT`와 `WITH`만 통과시킨다. 쓰기·스키마 변경·여러 문장은 거부한다.

## 하지 않는 것

- 서버, 계정, 클라우드 동기화 (필요하면 git이나 Dropbox로 각자)
- 의학적 진단이나 치료 제안
- 광고, 텔레메트리, 데이터 수집
